What is Cedar?

A language for writing and enforcing authorization policies

"Can this principal do this action on this resource?" 

permit ( principal == User::"alice",
         action    == Action::"view",
         resource  in  Album::"vacation" )
when { resource.owner == principal };
Let me start with what we're protecting. Cedar is a language for writing and enforcing authorization policies: it answers "can this principal do this action on this resource?" — the kind of check that gates every request to a service. This little policy is Cedar: permit alice to view the vacation album, but only when she owns the resource. Everything in this talk is about gaining confidence that the engine deciding this is right.
How we test it

We test Cedar differentially: one input, two engines, any mismatch is a bug

The method is only as strong as the inputs we feed both sides. But where do the inputs come from?

How do we get that confidence? Differential randomized testing. We take one random input — a schema, a policy, a request — and feed the exact same thing to two engines: our Lean specification, which carries machine-checked correctness theorems, and the Rust production implementation. If they ever disagree, that disagreement is a bug. It's a beautiful method, but notice the load-bearing assumption on this slide: it's only as good as the inputs we feed both sides. If we never generate the input that triggers a bug, we never find it. So the whole game comes down to input generation.

Hand-written, hand-maintained, hand-tuned to satisfy the Cedar type system.

Here's the catch. Those inputs come from a generator that is entirely handwritten — about 5,400 lines of Rust that took roughly six months to build, and it's still hand-maintained and hand-tuned every time the language evolves. Why so much effort? Because to be useful the inputs must be well-typed: they have to satisfy the full, intricate constraints of the Cedar type system, or the interesting code paths never get exercised. This generator is exactly what gives us confidence in the Rust implementation — it's genuinely needed. But it's a heavy, ongoing tax. The question that drives this project: can we get generators this good automatically?
The goal

Lift the burden: automate the generator.

But it must be as good as the handwritten one.

So what makes a generator good?

Two things at once. First, lift the burden — instead of hand-writing and hand-tuning the generator, derive it automatically. But, second, a derived generator is only worth anything if it's good — ideally as good as the handwritten one we're replacing. Which forces the question the rest of this section answers: what does "good" even mean for a generator?
The real measure

How well does it find bugs?

caught 2 of 5

The measure we actually want: bugs found ÷ bugs present. But real bugs are hidden — we can't compute it.

A good generator has a shot at finding a bug if one is present. If we could see every bug, "good" would be simple to measure: run the generator and count how many bugs it catches versus misses — bugs found over bugs present. But real bugs are hidden; if we knew where they were, we'd just fix them. So this measure isn't available at generation time — we need something we can actually compute, which is the next slide.
So we approximate

Can't see the bugs → chase throughput & coverage

Throughput
many draws
Coverage
wide spread

More draws (throughput) × wider spread (coverage) ⇒ better odds on a hidden bug — and the bar to clear is the handwritten generator.

Since we can't target hidden bugs, we maximize the two things that make a hit likely. Throughput — draws per second, so more shots on goal. And coverage — how widely those draws spread across the input space and the engine's code paths, so we aren't clustered in one corner. More draws times wider spread means better odds that some draw lands on whatever bug is hiding — and both are cheap to measure, unlike bug-count. The bar we have to clear is concrete: the existing handwritten generator. Every derived generator is judged on throughput and coverage against it.
What kills throughput

Rejection sampling: guess-and-check throws most draws away

✗ Guess & check

def genBST (lo hi : Nat) : Gen Tree := do
  let t ← genTree              -- any random tree
  if isBST lo hi t then
    pure t                     -- keep it
  else
    genBST lo hi               -- ✗ reject, try again

Almost every tree fails the check.

✓ Build by construction

def genBST (lo hi : Nat) : Gen Tree := do
  if lo > hi then pure .leaf else do
    let x ← choose lo hi   -- key in [lo,hi]
    let l ← genBST lo x
    let r ← genBST x hi
    pure (.node l x r)

Every draw is a valid BST.

So what wrecks throughput? Rejection sampling — guess-and-check. Here are two generators for the same thing, a binary search tree with keys in a range. On the left, the natural-but-naive one: generate any random tree, then test whether it happens to be a search tree; if not, throw it away and try again. As the tree grows, almost every random tree fails that test, so you burn nearly all your draws on rejects — throughput collapses. On the right, the same goal built by construction: pick each key already inside its valid interval and recurse, so every single draw is a valid BST, no retries. And notice the tell: rejection sampling is the retry branch — the "else, try again." It's right there in the source. That's the hook for the next slide: if we can spot that pattern without running the generator, we can approximate throughput statically.
Enter Specimen

Specimen turns choosing a generator into a search: a spec in, a generator out

A spec
an inductive relation
Specimen
enumerate & score schedules
A generator
valid inputs, by construction

Based on Rocq's QuickChick and my Testing Theorems, Fully Automatically (OOPSLA '26). My work made it handle Cedar's type system.

So the search we just motivated already exists as a tool: Specimen. The interface is exactly what you'd want — a spec goes in, a generator comes out. You hand it an inductive relation, it enumerates the candidate schedules and scores them statically, and it emits a generator that produces valid inputs by construction, no runs required. Specimen is based on Rocq's QuickChick and on my OOPSLA 2026 paper, Testing Theorems, Fully Automatically. What this project adds is making it actually handle something as large and intricate as Cedar's type system, which is the rest of the talk. Next: what exactly is that spec, and how does Specimen search it?
Specimen's domain

Deriving generators for inductive relations

The relation

inductive BST :
    Nat → Nat → Tree → Prop where
  | leaf : lo ≤ hi → BST lo hi .leaf
  | node :
      lo ≤ x ≤ hi →
      BST lo x l →
      BST x hi r →
      BST lo hi (.node l x r)

A mode → a generator

derive_mutual
  generator (fun lo hi => ∃ t, BST lo hi t)

Inputs lo hi, output t.

Fix a mode — which arguments are inputs, which is the output. The generator builds t by randomly applying a rule that fits, further constraining it, and recursing.

Specimen consumes an inductive relation in Lean — here BST, the same one we'll come back to. You point derive_mutual at it in a chosen mode: the mode says which of the relation's arguments are inputs and which is the output. Given the bounds lo and hi, produce a tree t with BST lo hi t. The derived generator builds t by construction: to produce a value it randomly selects one of the relation's rules whose conclusion can produce the target — leaf or node — applies it, which further constrains the output and creates sub-goals, and recurses on those sub-goals. The structure comes from the rules themselves; it doesn't reject-and-retry at the top. How it runs each rule's hypotheses — the ordering — is the knob Specimen tunes, next.
Reading a rule as a schedule

The leaf rule has one schedule — nothing to search

The rule

| leaf :
    lo ≤ hi →
    BST lo hi .leaf

Its only schedule

do
  check lo ≤ hi
  return .leaf

Both bounds are inputs, so lo ≤ hi is only checked — one generator, nothing to search.

Start with the easy rule. leaf says the empty tree is a BST whenever lo ≤ hi. Both bounds are inputs — the mode gives them — so the single hypothesis lo ≤ hi has nothing to produce; it can only be checked against the values already in hand. One hypothesis, both arguments bound, means exactly one schedule: check lo ≤ hi, then return the leaf. No ordering choice, nothing to search. The interesting case is node, where there are several hypotheses and the order genuinely matters.
What Specimen searches over

The node rule: three orderings of its hypotheses

bound second · 1 check

do
  (l, x) ← BST lo x l
  check lo ≤ x ≤ hi
  r ← BST x hi r
  return (node l x r)

bound third · 1 check, late

do
  (l, x) ← BST lo x l
  r ← BST x hi r
  check lo ≤ x ≤ hi
  return (node l x r)

bound first · 0 checks ✓

do
  x ← lo ≤ x ≤ hi
  l ← BST lo x l
  r ← BST x hi r
  return (node l x r)
produce
a ← P a
check
check P a

The heuristic scores fewest checks best — so across these orderings it keeps bound first.

Now node, which has real choices — its hypotheses are the bound lo ≤ x ≤ hi and the two subtree relations. Let me show the orderings that go wrong first. Bound second: let the left subtree run first, which produces the key x, but x wasn't constrained against hi, so the bound becomes a check before the right subtree — one check, one place to reject. Bound third: build both subtrees, then check the bound at the very end — still one check, but now you've wasted all that work before rejecting. Both of these check, and a check is a rejection. Now the winner: put the bound first — produce x directly inside the interval, and both subtrees follow with no failures. Zero checks, nothing rejected. That's the schedule Specimen keeps, and the whole search is just finding it.
The heuristic

Score each schedule on how likely — and how fast — it produces valid data

Valid by construction

How likely each draw is valid — fewer checks, fewer rejections.

Fast to produce

How quickly it runs — cheap steps, little backtracking.

Read statically off each schedule — an ordering of a rule's hypotheses. Specimen scores them all and keeps the best per rule: that's the generator.
Here's the heuristic itself. For a candidate schedule, Specimen estimates two things, both without ever running it. First, how likely it is to produce valid data by construction — a schedule with fewer checks rejects fewer draws, so more of what it makes is usable. Second, how fast it produces — cheap steps and little backtracking. Those two together are the score. And what it scores over are schedules: recall a schedule is one ordering of a rule's hypotheses, so each inductive rule has a small space of behavior-distinct orderings. Specimen enumerates that space, scores every schedule statically, and keeps the best one for each rule. Assemble the best schedule for every rule and you have the derived generator. No runs anywhere in the loop — that's what makes searching the whole space affordable.
The mismatch

But Specimen needs a relation — and Cedar's typechecker is a one-way function

Function typeOf

Unidirectional:
expr → type.
Can't run it backward to produce exprs of a target type.

Relation HasType

Multi-directional:
HasType e t.
Specimen can invert it into a generator.

Specimen derives generators from inductive relations, not functions.
So Specimen wants an inductive relation to invert. But Cedar's Lean specification isn't written that way — its typechecker is a function, typeOf, that maps an expression to its type. Functions are one-way: typeOf takes an expression and tells you the type, but you can't run it backward to ask "give me an expression of this type," which is exactly the generator we want. A relation, HasType e t, doesn't privilege a direction — you can fix either side and solve for the other. That's what Specimen needs. So the first job in applying Specimen to Cedar is converting the functional typechecker into a relational form.
The conversion

Claude rewrites typeOf as a relation — then we test it against the original

~1,200 lines, 44 relations. No proof — but the loop caught real gaps where the relation drifted.

I did that conversion with Claude, mostly Opus 4.8: it restates the functional typeOf as an inductive relation, HasType, about 1,200 lines and 44 inductive relations covering the language. But LLMs hallucinate — I can't just trust that the relation faithfully captures the typechecker. So I close the loop with Specimen itself: I derive a generator from the candidate relation, generate policies with it, and run those policies back through the real functional typeOf to confirm they actually get the intended type. There's no formal equivalence proof between the relation and the function — but this differential check is cheap and it caught real gaps where the relation drifted from the spec. That's the safety net around the LLM.

Before the results, the honest engineering story — because none of this worked out of the box. The Specimen I started from had four limits that a target as large as Cedar immediately exposed, and I'll flip each one to what I built for it. One: its scoring heuristic and weighting were fixed — one built-in strategy — so I made scoring and weighting modular, chosen at the derive site. Two: it had no introspection, a bad generator just failed silently — so I added the live readout, per-rule scores and schedules. Three: it only supported single-output modes, so it couldn't produce a relation with several outputs at once, like HasType — so I added multi-output modes. Four: deriving each dependency was manual, about twenty minutes of hand-wiring apiece — so I made derivation automatic and mutual, the whole web at once. Those four were step zero — making Specimen capable of Cedar at all.

Advancement · scoring

Dependency-aware scoring fixed scheduling; BudgetAware got real throughput

InitialScore
local sum — ignores dependencies
DensityScore
dependency-aware · Testing Theorems parity
BudgetAwareScore
check severity · recursion sizing
set_option specimen.scoreType "Scoring.BudgetAwareScore" in
derive_mutual
  generator (fun env => ∃ p, WellTypedPolicy env p)

Parity with Testing Theorems scoring improved scheduling but not full Cedar; distinguishing expensive vs cheap checks and preferring recursive calls did.

Now scoring, in two steps. First I brought Specimen to parity with the dependency-aware scoring from my Testing Theorems paper — a score that folds in the density of the sub-relations a rule depends on, not just the rule's own premises. That noticeably improved the rule scheduling, but it still couldn't handle full Cedar. So I added more: rules that distinguish the severity of checks — some checks are cheap, others are expensive to compute and really hurt throughput — plus sizing considerations, like preferring recursive calls over unrelated ones so the generator builds structure instead of thrashing, and more. Together those give BudgetAwareScore, and that's what finally produced good throughput. You select it with one set_option at the derive site.
Advancement · weighting

A weight modifier lifts a starved rule — hasTag to 63×

-- bias how often each rule fires
def favorHasTag (base : Nat) (rule : Name) : Nat :=
  match rule with
  | "hasTag" => base * 2 + 1   -- boost
  | _        => base

set_option specimen.weightModifier "favorHasTag" in …
Weighting is modular too, and it's literally a small function you write. favorHasTag takes a rule's base weight and returns a new one: for the starved tag rule it bumps the weight; everything else passes through unchanged. You select it with one set_option at the derive site — no change to the relation. The graph is the effect: fold-change in how often each construct appears, Specimen versus handwritten. HasTag goes from basically absent in the handwritten corpus, 0.27% of policies, to 17% under Specimen — a 63x boost, the single most Specimen-favored construct. That's how I fill in the rare-construct tail without touching the spec.
Putting it to work

With honest scores and a live readout, LLM-supported iteration converged

The readout flags a weak rule; fix the relation, the heuristic, or the weights, re-derive — until every feature is exercised.

With those in hand — dependency-aware scores and a live readout — iteration became a tight loop instead of a slog. I did LLM-supported iteration: derive, look at the chosen schedule and the per-rule scores, and spot the rule that's starving or backtracking. And there are three different remedies depending on the cause. Sometimes the relation rule itself is written in a way that doesn't properly constrain the data — so no ordering can avoid guessing — and the fix is to tighten the relation. Other times the relation is fine and the ordering heuristic just needs improving, so Specimen picks a better schedule. And sometimes a rule is simply too rare — the automatic weighting under-fires it — and a one-line weight modifier boosts it without touching anything else. The readout tells me which case I'm in. I kept going until the generator Specimen selected had good throughput and good coverage across the input grammar — every language feature actually exercised. At that point it was ready to race the handwritten one. Which brings me to results.

It found real bugs

The derived generator surfaced three genuine spec-vs-Rust divergences

1 · Actions escape their reserved type

Lean accepts an action UID of any entity type (e.g. name::"doc1"); Rust rejects.

2 · Extension types lose their qualifier

Schema Cedar::duration vs a duration(...) result: Rust rejects; Lean's ExtType collapses them and accepts.

3 · Spurious tagNotFound on a projected-record getTag — Lean stores records as a non-canonical ordered list, so the receiver decodes in a different attribute order and misses the capability. Fix: sort record attrs on decode.
And it earned its keep — three real divergences between the spec and Rust, each surfaced inside these hour-long runs. One: actions escaping the reserved Action type. Lean happily accepts an action whose UID has any entity type, like name colon-colon "doc1", where Rust correctly rejects it — actions are supposed to live in a reserved namespace. Two: extension types losing their qualifier. A schema attribute typed as Cedar::duration versus a value produced by the duration extension function — Rust distinguishes them and rejects the mismatch, but Lean's ExtType enum collapses the two and accepts. Three, the subtle one: a spurious tagNotFound on getTag through a projected record. Lean rejects a perfectly valid policy that Rust accepts, because Lean stores records as a non-canonical ordered list — so getTag's receiver can decode attributes in a different order and lose track of the capability that proves the tag exists. The fix is to sort record attributes on decode. Three genuine bugs from a declarative relation.
Bug deep-dive · #3

A valid getTag Lean rejects — because it stores records in a non-canonical order

The policy

Read a tag off a projected record — ({…}).getTag(k).

Rust: well-typed ✓

Lean: tagNotFound ✗

Why Lean is wrong

Records are stored as an ordered list, not canonicalized.

The projected receiver decodes attributes in a different order.

The capability proving the tag exists is keyed to that order → lost.

Fix: canonicalize — sort record attributes on decode. A genuine spec bug, surfaced by a generator no one hand-tuned.
Let me explain the subtle one, because it shows the payoff. The policy reads a tag off a record that's been projected — a getTag on a record expression. Rust's validator says it's well-typed; Lean's says tagNotFound and rejects it. Neither is a generator bug — it's a real divergence in the spec. The cause: Lean stores records as an ordered list of attributes that isn't canonicalized, so when the projected receiver is decoded its attributes can come back in a different order. Cedar tracks, as a capability, the fact that a given tag is known to exist — and that capability is keyed to the attribute order, so under the reordering it gets lost, and the typechecker concludes the tag might not be there. The fix is to canonicalize records on decode by sorting their attributes. The point for this talk: a declarative relation, with a generator nobody hand-tuned, surfaced a genuine bug in the specification.
Takeaways

One relational spec of the validator yields a near-complete generator for valid Cedar

Why it's a win

• Covers the valid fragment of Cedar almost entirely — from one relational spec.

• Saturates coverage in seconds — ideal for short campaigns (a bugfix, a new feature).

• Weighting is derived automatically — a single constructor override, vs hand-weighting every constructor.

• Free with the spec: if the Lean model goes relational, the generator updates with it.

• Sound: 0 spurious mismatches over ~2.9M validations.

Next steps

• Specify the error semantics — cover the validator's erroring paths the spec can't yet model.

• Coverage-guided Specimen — feed coverage back into the schedule search.

• Drop-in adoption in Cedar's fuzzing pipeline.

The takeaways. The core result: from a single relational spec based on the functional validator, Specimen derives a very good generator for the valid — almost entirely valid — fragment of Cedar policies. A few things that makes worthwhile. It saturates line coverage in seconds, which makes it ideal for short fuzzing campaigns — exactly when you're iterating on a bugfix or a new feature and don't want a half-hour warmup. Its weighting heuristics are derived automatically from the scored quality of each typing rule; the only hand-tuning is a single constructor override, whereas a handwritten generator has to be carefully weighted by hand for every constructor. And if the Lean model ever switches over to the relational spec, the generator comes for free with any update to the spec. It's also sound — zero spurious mismatches over about 2.9 million validations. Next steps: write a specification of the error semantics so we cover the erroring portions of the validator that the spec currently can't represent; feed coverage back into the schedule search for a guided Specimen; and drop it into Cedar's real fuzzing pipeline. Thank you.
