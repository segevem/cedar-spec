What is Cedar?

A language for writing & enforcing authorization policies — can this principal do this action on this resource?

permit (
  principal == User::"alice",
  action    == Action::"view",
  resource  in  Album::"vacation"
) when { resource.owner == principal };

Cedar is used in production for authorization — so its correctness is not optional.

How Cedar Stays Correct: Differential Testing

Same input → Lean specification and Rust implementation; a mismatch is a bug. But where do the inputs come from?

This is differential randomized testing (DRT). The Lean spec carries machine-checked correctness theorems (authorization soundness, etc.); production is Rust. Note: the relation Specimen actually consumes is a differential-tested restatement of the typechecker, not the proven theorems themselves. The whole method is only as good as the inputs we feed both sides — that's what this project is about.

A Generator is Costly to Build and Maintain

~5,400 lines of Rust · ~6 months to build · hand-updated for every new Cedar feature

What Specimen Does

Point it at an inductive relation; it generates random values that satisfy it — correct by construction.

-- `n` is a perfect cube
inductive IsCube : Nat → Prop
  | mk (m) : IsCube (m * m * m)

-- a (false) property to test
∀ n, IsCube n → n ≤ 27

 Rejection sampling: random naturals are almost never cubes → discarded.

 Specimen (by construction): generates cubes directly — pick m, output m³.

 Quick demo.

The generator is the relation run backwards — no rejection sampling.

Using Specimen: the API

Point derive_mutual at a relation; it returns a generator whose outputs satisfy that relation.

-- steer the SEARCH — how candidate schedules are scored
set_option specimen.scoreType      "Scoring.BudgetAwareScore" in
-- steer GENERATION — how often each rule fires
set_option specimen.weightModifier "favorHasTag"             in
derive_mutual generator (fun env c ty => ∃ x cout, HasType x c env ty cout)

-- a weight modifier is just a function over constructors:
def favorHasTag (base : Nat) (ctor : Name) … : Nat :=
  match ctor with
  | .str _ "hasTag" => base * 3 + 1   -- emit `hasTag` ~3× more often
  | _               => base           -- everything else unchanged

Pluggable scoring

Pick the strategy that ranks candidate generators (density, worst-leaf, graded).

Pluggable weighting

Bias how often each rule fires, via composable weight modifiers.

My work made scoring & weighting modular — extend them in your own file, no Specimen fork needed.

Specimen is built on QuickChick ideas + "Testing Theorems, Fully Automatically" (OOPSLA '26, to appear). The two knobs above are the whole user-facing surface: what relation to derive from, and how to steer the search. I won't go into the search internals here.

The Input: Cedar's Typechecker as a Relation

Cedar's typechecker is a function. Specimen needs an inductive relation — so we wrote one.

Cedar's functional spec

def typeOf : Expr → Result …
  | .and x₁ x₂ =>
    match typeOf x₁ with
    | .bool .ff => (.bool .ff, ∅)
    | .bool b₁  =>
      match typeOf x₂ with
      | .bool b₂ => andTy b₁ b₂
      | _        => error
  | …

Our relational spec

inductive HasType : Expr → … → Prop
  | andShort :
    HasType x₁ … (.bool .ff) … →
    HasType (.and x₁ x₂) … (.bool .ff)
  | and :
    HasType x₁ … (.bool b₁) … →
    HasType x₂ … (.bool b₂) … →
    HasTypeAnd b₁ b₂ … ty … →
    HasType (.and x₁ x₂) … ty …

Evolving the Scoring Heuristic

The scoring strategy decides how Specimen turns the relation into a generator. Reaching a good one took three stages.

ScoringKey ideaGot us to
①InitialScorelocal sum: checks + length + unconstraineda start — but blind to what a schedule's dependencies cost
②DensityScoredependency-aware: categorical density (Total / Partial / Backtracking / Checking) that folds in the density of the sub-relations a schedule callsa working generator for an incomplete reconstruction of Cedar
③BudgetAwareScoredensity + throughput heuristics: fabrication, selectivity, localitytolerable throughput on the full spec — the generator we ship

Each stage keeps the previous one's guarantees and adds what the next bottleneck demanded — from "does it derive at all?" to "does it derive fast enough?"

A Schedule Reorders a Rule to Avoid Checks

The rule for e₁ in e₂ has four premises. A check is a rejection-sampling step — the scoring heuristic searches for the ordering that turns checks into producers.

ValidEntityType t₁ → Descendant t₁ t₂ →              -- t₁ declared, t₂ ⊑ t₁
HasType e₁ (entity t₁) → HasType e₂ (entity t₂) → HasType (e₁ in e₂) Bool

Bad ordering → rejection sampling

t₁ ← any entity type    -- guess
t₂ ← any entity type    -- guess
e₁ ← term : entity t₁
e₂ ← term : entity t₂
check ValidEntityType t₁   ✗
check Descendant t₁ t₂     ✗   -- usually fails → retry

2 checks — most draws discarded

Better ordering → produce

t₁ ← ValidEntityType    -- drawn from the schema
t₂ ← Descendant t₁      -- a descendant of t₁
e₁ ← term : entity t₁
e₂ ← term : entity t₂
-- nothing left to check

0 checks — every draw valid

The heuristic scores orderings by how few checks they leave. BudgetAwareScore refines this — e.g. don't produce a variable from an unbounded source (record types) when a finite relation can.

And It Found Real Bugs

Three genuine spec-vs-implementation divergences — the Lean spec and cedar-policy disagree on valid inputs:

1   Actions escape the reserved Action type. Lean accepts an action UID of any entity type (e.g. name::"doc1"); cedar-policy requires the reserved Action type and rejects. Lean never encodes the constraint.

2   Extension types lose their qualifier. Schema attr Cedar::duration vs a duration(…) result: Rust rejects (Cedar::duration ≠ duration); Lean's ExtType enum collapses both and accepts.

3   Spurious tagNotFound on a projected-record getTag. Lean rejects a valid policy (Rust accepts): it stores records as a non-canonical ordered list, so getTag's receiver can decode in a different attribute order and miss the capability. Fix: sort record attrs on decode.

A spec-derived generator is a lens on the spec vs. the implementation — divergences neither side's own tests had surfaced.

Bottom Line

Derived from the spec

Comes close to handwritten on line coverage once out-of-scope lines (errors, annotations) are excluded.
Higher structural diversity, competitive throughput.
Found 3 real bugs, each within hour-long runs.
Auto-derived — a declarative relation replaces 5,400 lines of imperative Rust.

Complementary, not a total replacement

Handwritten still adds value for features the Lean spec can't model (e.g. template slots), for error paths, and for the ~100–150 validator lines specimen doesn't reach.

An unguided, spec-derived generator comes close to a coverage-guided handwritten one on line coverage (once out-of-scope lines are excluded), with higher diversity, competitive throughput, and 3 real bugs found — trading a hand-maintained imperative generator for a declarative spec.
