Cedar Enforces Authorization in Production

permit (
  principal == User::"alice",
  action    == Action::"view",
  resource  in  Album::"vacation"
) when { resource.owner == principal };

Can this principal do this action on this resource?

Cedar is a policy language for authorization, used in production (e.g. Amazon Verified Permissions). Because it decides who can access what, its correctness is not optional.

Cedar Is Tested by Feeding the Spec and Rust the Same Inputs

Same input → spec vs. Rust; a mismatch is a bug. But where do the inputs come from?

Differential randomized testing (DRT). The Lean spec carries machine-checked correctness theorems; production is Rust. The method is only as good as the inputs we feed both sides — that is what this project is about.

Our Confidence in Rust Rests on a Costly, Hand-Tuned Generator

Hand-written, hand-maintained, hand-tuned to satisfy the Cedar type system.

~5,400 lines of Rust · ~6 months to build · still costs time to maintain.

Cedar's differential testing relies on a generator that produces inputs satisfying the complex constraints of the Cedar type system — and it's hand-written, hand-maintained, and hand-tuned. It is genuinely needed: it is what gives us confidence in the production Rust implementation. But it was time-consuming to set up and still consumes time to maintain and tune as Cedar evolves. That burden is what we want to relieve.

Goal: Construct Good Generators Automatically

Lift the burden — derive the generator instead of writing it.

But what makes a generator good?

To relieve that burden, we want to construct good generators automatically instead of by hand. Which raises the question that drives the rest of the talk: what is a good generator?

Bugs hide in the space of inputs

A Good Generator Finds Bugs — Proxy by Throughput & Coverage

Throughput
many inputs,
fast
Coverage
diverse inputs;

Can't measure it directly → proxy by throughput & coverage, vs. handwritten.

A good generator has a shot at finding bugs if they're present. That's hard to measure directly, so we proxy it with throughput (inputs per second) and coverage (how much of the input grammar, how many code paths). So any automatically derived generator should be compared, on exactly those two metrics, against the handwritten generator.

A Generator Is an Ordering of a Rule's Premises

-- one rule → generate its premises in some order
ValidEntityType t₁ → Descendant t₁ t₂ →
HasType e₁ (entity t₁) → HasType e₂ (entity t₂) →
HasType (e₁ in e₂) Bool
n!
orderings per rule — one candidate generator each
✗ measure
throughput/coverage need repeated timed trials for significance

Each ordering is a candidate generator → the space is vast → we can't measure our way through it.

The metrics are expensive: throughput and coverage take time and repeated trials to get significant results. And the space of generators is vast — we can enumerate it as the space of orderings of the hypotheses in each inductive rule the generator satisfies. That's what Specimen is built on. With n! orderings per rule, we cannot use those slow metrics to work through the space.

Score Generators Statically — Penalize What Hurts Throughput and Coverage

Backtracking
retries waste time → lower throughput
A rule that keeps failing
each rule = a language feature with its own sub-generator; if it rarely fires, that feature is under-covered
Rejection sampling
wastes time and starves rules — the simple target

A cheap static score per candidate, instead of expensive timed trials.

Instead of measuring, score statically with heuristics. They must penalize sources of lowered throughput — like generators that backtrack a lot — and sources of lowered coverage. On coverage: each typing rule describes a different feature of the language, and each gets its own sub-generator; if a rule's generator often fails to produce anything satisfying it, that feature is damaged in coverage. Rejection sampling is the simple target that hits both — the more of it, the more time wasted and the more rules starved.

Random Trees Are Almost Never BSTs — Specimen Builds Them by Construction

inductive BST : Nat → Nat → Tree → Prop
  | leaf : lo ≤ hi → BST lo hi .leaf
  | node : lo ≤ x → x ≤ hi →
           BST lo x l → BST x hi r →
           BST lo hi (.node l x r)

 Random trees are almost never sorted → discarded.

 Split the bound at the key, recurse → always a BST.

 Quick demo.

Recursion and an ordering constraint — built, not filtered. (BstDemo.lean)

Binary search tree: recursive, and the ordering constraint makes keys depend on their subtree bounds. Random trees almost never satisfy it, so rejection sampling fails. Specimen reads the rule backwards — pick a key in the bound, split the bound around it, recurse — so every tree it emits is a valid BST.

Reordering a Rule's Premises Turns Checks Into Producers

A check is a rejection-sampling step. The heuristic reorders to remove them.

ValidEntityType t₁ → Descendant t₁ t₂ →              -- t₁ declared, t₂ ⊑ t₁
HasType e₁ (entity t₁) → HasType e₂ (entity t₂) → HasType (e₁ in e₂) Bool

Bad ordering → rejection sampling

t₁ ← any entity type    -- guess
t₂ ← any entity type    -- guess
e₁ ← term : entity t₁
e₂ ← term : entity t₂
check ValidEntityType t₁   ✗
check Descendant t₁ t₂     ✗   -- usually fails → retry

2 checks — most draws discarded

Better ordering → produce

t₁ ← ValidEntityType    -- drawn from the schema
t₂ ← Descendant t₁      -- a descendant of t₁
e₁ ← term : entity t₁
e₂ ← term : entity t₂
-- nothing left to check

0 checks — every draw valid

Score orderings by how few checks they leave.

Concretely: the same rule, two orderings. Guessing t₁/t₂ first forces two checks that usually fail — rejection sampling. Producing t₁ from the schema, then t₂ as a descendant, leaves nothing to check. BudgetAwareScore refines this further — e.g. don't produce a variable from an unbounded source when a finite relation can.

Choosing a Generator Becomes Static-Score Optimization

generator = arg min schedules  staticCost(schedule)
Search the schedule space
Score each statically
Emit the best generator

This is the heart of Specimen.

Put together: picking a generator is an optimization — search the space of schedules, score each with the static heuristic, emit the lowest-cost one. That reframing, and a good heuristic, is what Specimen is.

A Type System Is Just Another Relation — and Specimen Finds Bugs

Generate well-typed λ-terms from the typing relation; run a big-step evaluator with a planted bug.

| app f a => do let (.vclos cenv _ body) ← eval env f | none
                let v ← eval env a
                eval cenv body        -- BUG: forgot to bind the arg (should be `v :: cenv`)

 Quick demo.  (StlcDemo.lean)

A typing relation is the same shape as a BST relation — just for terms. Specimen generates well-typed terms; run them through a buggy evaluator and it surfaces a counterexample in seconds. Cedar's typechecker is exactly this kind of relation — which points at the one obstacle.

Cedar's Typechecker Is a One-Way Function — We Invert It to a Relation

Functional (one-way)

def typeOf : Expr → Result …
  | .and x₁ x₂ =>
    match typeOf x₁ with
    | .bool .ff => (.bool .ff, ∅)
    | .bool b₁  =>
      match typeOf x₂ with
      | .bool b₂ => andTy b₁ b₂
      | _        => error
  | …

Relational (invertible)

inductive HasType : Expr → … → Prop
  | andShort :
    HasType x₁ … (.bool .ff) … →
    HasType (.and x₁ x₂) … (.bool .ff)
  | and :
    HasType x₁ … (.bool b₁) … →
    HasType x₂ … (.bool b₂) … →
    HasTypeAnd b₁ b₂ … ty … →
    HasType (.and x₁ x₂) … ty …

A function only runs term → type. To produce a term of a given type, Specimen needs the relation.

Specimen relies on an inductive relational specification. Cedar's Lean spec is written as functions, which — unlike relations — are unidirectional. To invert a function like typechecking into a generator that produces terms of a given type, we convert it to relational form. That relation is what Specimen consumes.

I convert the functional spec to a relation with Claude (mostly Opus 4.8). LLMs hallucinate, so to trust the relation I use Specimen itself: derive a generator from it, generate policies, and check each has the type the functional typeOf assigns. The tool validates its own input.

Made Specimen's Scoring Dependency-Aware and Modular

Built-in score ignored the quality of the generators a rule depends on → iterating on the relation was painful.

ScoringKey ideaGot us to
①InitialScorelocal sum of checks + lengthblind to dependency cost
②DensityScoredependency-aware: folds in sub-relation densitya working generator
③BudgetAwareScore+ throughput heuristics: fabrication, selectivity, localitythe generator we ship

Structure from my OOPSLA '26 paper, Testing Theorems, Fully Automatically — dependency-aware, extend in your own file.

Specimen's built-in scoring was so simple that a generator's quality didn't take into account the quality of the generators it depended on — which made iterating on the relation difficult. I augmented Specimen with a modular scoring and weighting system, based on the structure I used in my OOPSLA 2026 paper "Testing Theorems, Fully Automatically," which allows scoring that takes dependencies into account. Three stages got us to shippable throughput.

Enabled Mutual Derivation and a Live Schedule/Score Readout

Mutual derivation

Deriving each dependency separately was slow on every relation change — and blocked mutual recursion (typecheck ↔ infer). Now they derive together.

Live readout

See the chosen schedule and score for every rule — so I can find and fix the weak generator.

Both turn slow, opaque iteration into a fast feedback loop.

Two more blockers to rapid iteration. First, Specimen required every dependency to be derived separately; when a change to the relation led to different required dependencies, that added a lot of slowdown — and it meant dependencies couldn't be mutually recursive, which is often the natural solution, since typechecking and type inference are frequently mutually recursive. I enabled mutual derivation. Second, to improve how I assess candidate generators, I added a visual and textual readout of the selected generator's structure — the schedule it chooses for each inductive rule and their scores.

And It Found Three Real Spec-vs-Rust Divergences

1   Actions escape the reserved Action type — Lean accepts, Rust rejects.

2   Extension types lose their qualifier — Rust rejects, Lean accepts.

3   Spurious tagNotFound on a projected-record getTag — Lean rejects, Rust accepts.

A spec-derived generator is a lens on spec vs. implementation — three, each within hour-long runs.

Three genuine divergences. (1) Lean accepts an action UID of any entity type (e.g. name::"doc1"); Rust requires the reserved Action type. (2) A schema attr Cedar::duration vs a duration(…) result — Rust rejects, Lean's ExtType enum collapses them and accepts. (3) Lean spuriously rejects a valid policy: it stores records as a non-canonical ordered list, so getTag's receiver can decode in a different attribute order and miss the capability — fix is to sort record attrs on decode. Each surfaced within hour-long runs.
