The subject

Cedar decides who can do what — so it must be correct

"Can this principal do this action on this resource?"

A production authorization language. Correctness is not optional.

permit ( principal == User::"alice",
         action    == Action::"view",
         resource  in  Album::"vacation" )
when { resource.owner == principal };
Let me start with what we're protecting. Cedar is a production authorization-policy language: it answers "can this principal do this action on this resource?" — the kind of check that gates every request to a service. Because it sits on the security-critical path, correctness is not a nice-to-have; a wrong answer is either a lockout or a breach. This little policy is Cedar: permit alice to view the vacation album, but only when she owns the resource. Everything in this talk is about gaining confidence that the engine deciding this is right.
How we test it

How do we get that confidence? Differential randomized testing. We take one random input — a schema, a policy, a request — and feed the exact same thing to two engines: our Lean specification, which carries machine-checked correctness theorems, and the Rust production implementation. If they ever disagree, that disagreement is a bug. It's a beautiful method, but notice the load-bearing assumption on this slide: it's only as good as the inputs we feed both sides. If we never generate the input that triggers a bug, we never find it. So the whole game comes down to input generation.

Here's the catch. Those inputs come from a generator that is entirely handwritten — about 5,400 lines of Rust that took roughly six months to build, and it's still hand-maintained and hand-tuned every time the language evolves. Why so much effort? Because to be useful the inputs must be well-typed: they have to satisfy the full, intricate constraints of the Cedar type system, or the interesting code paths never get exercised. This generator is exactly what gives us confidence in the Rust implementation — it's genuinely needed. But it's a heavy, ongoing tax. The question that drives this project: can we get generators this good automatically?
The goal, and the obstacle

Derive generators automatically — but first, what makes one "good"?

So the plan is to construct good generators automatically, to lift that maintenance burden. But that immediately raises the real question: what is a good generator? The honest answer is: one that has a shot at finding a bug if a bug is present. That's the definition we actually care about. The problem is you can't measure it directly — you don't know where the bugs are, and "did it find a bug" is a rare, noisy, all-or-nothing signal. So we need something we can actually measure that stands in for bug-finding power.
Measurable proxies

The proxies are throughput and coverage. Throughput is how many valid inputs we produce per second — more shots on goal. Coverage is how much of the engine those inputs actually exercise — more of the target surface. Together they're a reasonable stand-in for bug-finding power: more inputs times more of the code reached means more chances to trip something. And crucially, these give us a bar to clear: any automatically derived generator has to be compared, on throughput and coverage, against the handwritten one we're trying to replace. That comparison is the whole evaluation.
Why we can't just measure our way there

The generator space is enormous — and the metrics are too slow to search it

Metrics are expensive

Throughput & coverage need long runs and many repeated trials for a significant result.

The space is vast

A generator = an ordering of a rule's premises.
n premises → n! orderings.

Can't run hour-long trials on every one of n! candidates. Need something cheap and static.
Now, why not just measure every candidate and pick the best? Two reasons collide. First, the metrics are expensive: to get a statistically significant throughput or coverage number you need long runs and many repeated trials. Second, the space of candidate generators is huge. And I can say "huge" precisely — because we can enumerate that space. A generator for data satisfying an inductive rule is just an ordering of that rule's premises, a schedule. n premises gives n factorial orderings, and that's per rule, across dozens of rules. You cannot run hour-long trials across a factorial space. So we need something cheap and static to score candidates without running them.
The static signal

Reorder premises to turn rejection-sampling checks into producers

A "check"
guess, then test — discard on fail
A "producer"
generate a value that fits by construction

Backtracking wastes time → penalize it (throughput).

A rule that often fails to produce starves its language feature → penalize it (coverage).

The simplest lever: minimize rejection sampling.

Here's the static signal we exploit. Within a rule, each premise can play one of two roles depending on where it sits in the ordering. If its inputs are already fixed, it becomes a check — you guessed some values, now you test the premise and throw the draw away if it fails. That's rejection sampling. But if you reorder so the premise runs first, it becomes a producer — it generates a value that satisfies itself by construction. Same premise, different role, purely from ordering. Our heuristics score orderings by penalizing two things. Backtracking, because it wastes time and kills throughput. And rules whose generators often fail to produce anything, because each rule is a language feature, and a starved rule means that feature is under-covered. The simplest thing to chase: minimize rejection sampling.

Let me make this concrete with something everyone knows: binary search trees. Here's the demo. If I generate a random tree and then check whether it happens to satisfy the search-tree ordering invariant, almost every tree fails — the probability a random tree is a BST collapses as it grows, so I'm rejecting nearly everything and getting very few, very small examples. That's the guess-and-check trap. Now watch the reordered version: instead of checking the invariant afterward, I push the bounds inward and draw each node's value inside the valid interval its position allows. Every single draw is a valid BST, zero checks. Same specification, and just by ordering the work right, rejection sampling goes to nothing. That's the entire idea of Specimen in miniature — and this is BstDemo.lean, which is runnable.
Worked example — a real Cedar rule

The e₁ in e₂ rule: one ordering discards most draws, another discards none

-- rule: HasType (e1 in e2) Bool  requires 4 premises
ValidEntityType t1   Descendant t1 t2   HasType e1 (entity t1)   HasType e2 (entity t2)

Bad ordering — 2 checks

Guess t1, t2, then:

check ValidEntityType t1 ✗

check Descendant t1 t2 ✗

most draws discarded

Good ordering — 0 checks

draw t1 from ValidEntityType

draw t2 as a Descendant of t1

then the terms e1, e2

every draw valid

Here's the exact same phenomenon in Cedar. This is the typing rule for the "in" operator — e1 in e2 has type Bool — and it has four premises: t1 must be a valid entity type, t2 must be a descendant of t1 in the hierarchy, and e1 and e2 must have those entity types. A naive ordering guesses t1 and t2 out of thin air, then checks ValidEntityType and checks Descendant. Both are checks, both usually fail — you're picking random type names and hoping two of them happen to be in a subtype relationship. Almost everything is discarded. The good ordering draws t1 directly from the ValidEntityType relation, draws t2 as a descendant of t1, and only then generates the terms. Zero checks, every draw valid. The reordering is the whole win, and it's invisible to the functional spec — you only see it once the rule is relational.
The heart of Specimen

Picking a generator becomes an optimization over cheap static scores

generator*  =  arg max ordering ∈ n!   Score(ordering)
Enumerate orderings
Score statically
no runs needed
Take the best
Put those pieces together and the whole problem of "get me a good generator" turns into an optimization. Enumerate the orderings of each rule's premises, score each one statically with the cheap heuristics — penalizing backtracking and starvation, rewarding producers over checks — and take the argmax. No hour-long runs in the loop; the scoring is static. That reframing, generator selection as optimization over a static score, is the heart of Specimen. Everything after this is about making the score good enough that its argmax is actually the generator you'd have chosen if you could afford to measure.
The mismatch

But Specimen needs a relation — and Cedar's typechecker is a one-way function

Function typeOf

Unidirectional:
expr → type.
Can't run it backward to produce exprs of a target type.

Relation HasType

Multi-directional:
HasType e t.
Specimen can invert it into a generator.

Specimen derives generators from inductive relations, not functions.
So Specimen wants an inductive relation to invert. But Cedar's Lean specification isn't written that way — its typechecker is a function, typeOf, that maps an expression to its type. Functions are one-way: typeOf takes an expression and tells you the type, but you can't run it backward to ask "give me an expression of this type," which is exactly the generator we want. A relation, HasType e t, doesn't privilege a direction — you can fix either side and solve for the other. That's what Specimen needs. So the first job in applying Specimen to Cedar is converting the functional typechecker into a relational form.

I did that conversion with Claude, mostly Opus 4.8: it restates the functional typeOf as an inductive relation, HasType, about 1,200 lines and 44 inductive relations covering the language. But LLMs hallucinate — I can't just trust that the relation faithfully captures the typechecker. So I close the loop with Specimen itself: I derive a generator from the candidate relation, generate policies with it, and run those policies back through the real functional typeOf to confirm they actually get the intended type. There's no formal equivalence proof between the relation and the function — but this differential check is cheap and it caught real gaps where the relation drifted from the spec. That's the safety net around the LLM.

Quick bridge to show this isn't Cedar-specific. Cedar's type system is elaborate, but structurally it's just a typing relation — and any typing relation works the same way. In StlcDemo.lean I take the simply-typed lambda calculus: its typing rules are a relation, Specimen inverts them to generate well-typed terms by construction, and when I point those terms at an evaluator with a deliberate bug planted in it, a counterexample falls right out. Same machinery, tiny language. It's the clean version of exactly what we're doing to Cedar's much larger typechecker.
Contribution 1 — scoring

I made scoring dependency-aware, so a generator's score reflects what it depends on

InitialScore
local sum — ignores dependency cost
DensityScore

BudgetAwareScore

A modular scoring + weighting system — structure from "Testing Theorems, Fully Automatically" (OOPSLA 2026). We ship BudgetAware.
Now the two contributions that made iterating on this actually feasible. First, scoring. Specimen's original score was too simple: a local sum over a rule's own premises that ignored the cost of the generators it depended on. So a rule could look great while secretly leaning on a dependency that backtracks constantly — and you couldn't tell from the score. I rebuilt scoring as a modular, dependency-aware system, using the structure from my OOPSLA 2026 paper, "Testing Theorems, Fully Automatically." It evolves in three stages: the old local InitialScore; DensityScore, which folds in the density of the sub-relations you depend on; and BudgetAwareScore, which adds throughput heuristics — fabrication, selectivity, locality. BudgetAware is what we ship. The point is the score now composes down the dependency tree, so iterating on the relation gives honest feedback.
Contribution 2 — derivation & visibility

Mutual derivation plus a live readout turned iteration from days into a loop

Mutual derivation

All dependencies derived together — not one-at-a-time on every change.

Unlocks mutual recursion (typecheck ↔ infer).

Live schedule readout

Visual + text view of the chosen schedule and score per rule.

See why a candidate was picked — and what's weak.

Second contribution, two parts. Before, Specimen derived every dependency separately, so any change to the relation that shifted which dependencies were needed forced a slow re-derivation of each one — and worse, it couldn't express mutually recursive dependencies at all. That's a real limitation, because typechecking and type inference are naturally mutually recursive, and so are pieces of Cedar's typing. So I added mutual derivation: all the dependencies get derived together, which both speeds up the change loop and unlocks mutual recursion. The other part is visibility. I built a visual and textual readout of the selected generator — the schedule it chose for each inductive rule and the score of each. Now when a candidate is picked I can see why, and which rules are weak, instead of guessing.

With those two in hand — dependency-aware scores and a live readout — iteration became a tight loop instead of a slog. I did LLM-supported iteration on both the scoring heuristic and the relation itself: adjust, look at the chosen schedule and the per-rule scores, spot the rule that's starving or backtracking, fix it, and repeat. The setup. I evaluate on two real differential-testing targets: the validator and the symbolic compiler. Each run is up to an hour, repeated about 20 times, with 95% bootstrap confidence intervals, so the numbers are statistically honest rather than one lucky run. One important fairness point on coverage: the Lean spec simply cannot represent about 2,680 lines of Rust error-handling code — those paths have no counterpart in the spec, so no spec-derived generator could ever hit them. I report a fair coverage number that excludes those lines. And note the handicap runs against me: the handwritten generator gets coverage-guided fuzzing via cargo-fuzz — feedback steering it toward new code — whereas Specimen just emits valid inputs blindly, by construction, with no feedback loop.

Here's the whole comparison on one card. Fair line coverage: essentially parity — a Jaccard of about 0.95 shared lines, with roughly 100 to 150 lines unique to each side, so they're covering nearly the same set and each reaches a little the other doesn't. Where the derived generator pulls ahead is structure: its policies are three to five times larger and more structurally diverse per policy — more nodes, more shapes, deeper nesting. Throughput: the derived generator runs around 1,700 valid inputs per second versus 300 to 500 for handwritten, so it's several times faster despite producing bigger policies. And soundness: after I fixed some generator-soundness issues, zero spurious mismatches across about 2.9 million validations — so when it does flag a disagreement, you can trust it.
It found real bugs

The derived generator surfaced three genuine spec-vs-Rust divergences

1 · Actions escape their reserved type

Lean accepts an action UID of any entity type (e.g. name::"doc1"); Rust rejects.

2 · Extension types lose their qualifier

Schema Cedar::duration vs a duration(...) result: Rust rejects; Lean's ExtType collapses them and accepts.

3 · Spurious tagNotFound on a projected-record getTag — Lean stores records as a non-canonical ordered list, so the receiver decodes in a different attribute order and misses the capability. Fix: sort record attrs on decode.
And it earned its keep — three real divergences between the spec and Rust, each surfaced inside these hour-long runs. One: actions escaping the reserved Action type. Lean happily accepts an action whose UID has any entity type, like name colon-colon "doc1", where Rust correctly rejects it — actions are supposed to live in a reserved namespace. Two: extension types losing their qualifier. A schema attribute typed as Cedar::duration versus a value produced by the duration extension function — Rust distinguishes them and rejects the mismatch, but Lean's ExtType enum collapses the two and accepts. Three, the subtle one: a spurious tagNotFound on getTag through a projected record. Lean rejects a perfectly valid policy that Rust accepts, because Lean stores records as a non-canonical ordered list — so getTag's receiver can decode attributes in a different order and lose track of the capability that proves the tag exists. The fix is to sort record attributes on decode. Three genuine bugs from a declarative relation.

Bottom line. An unguided, spec-derived generator rivals a coverage-guided handwritten one on fair line coverage, beats it on structural diversity, stays competitive — actually faster — on throughput, and found three real bugs. And it comes from a declarative relation, roughly 1,200 lines, instead of 5,400 lines of hand-tuned Rust that took six months. I want to be clear it's complementary, not a replacement: the handwritten generator still owns things Specimen doesn't reach — template slots, the error paths, that 100-to-150 validator lines. The best setup uses both. Where this goes next: first, coverage-guided Specimen — feed the coverage signal back into the schedule search, so the argmax is informed by what actually got hit, which should close the remaining error-path gap. And second, drop-in adoption into Cedar's real fuzzing pipeline so this runs continuously. Thank you.
